### Funadansu の移行のフェーズ

| フェーズ | 目的（ゴール） | 主な中身 | リリース |
| --- | --- | --- | --- |
| **最終** | 旧基盤の API が提供する機能を満たした、Cloudflare（Hono）と Go のアプリケーションがデプロイ可能であること。判定：旧 E2E がフェーズ0のベースライン以上に通る | **移行 CLI と OIDC はスコープ外** | — |
| **0** | 各ポリレポの移行作業ができる状態。**Bootstrap が動き（Hono の proxy〈Cloudflare とコンテナ〉と、コンテナの Go がつながり、Bootstrap のエンドポイントのテストが通る）、旧基盤の E2E が Funadansu に向けて動いて全部 RED** | 下の「フェーズ0のタスク」 | — |
| **1** | 既存の DB（旧スキーマ、Aurora 互換）のまま、**アプリだけ差し替えられる** | 最初の単位：Hono の proxy と JWT（独自セッションをはがす）。続いて Go への愚直なポーティング | タグ |
| **2** | エンドポイントはそのまま、CQRS で分離 | 旧スキーマのまま関数を分ける | タグ |
| **3** | DB の統合 | 統合スキーマ、**CockroachDB への対応はここから**（CI も両方に）、**読み取り側の複製（Cloudflare）は統合の後** | タグ |
| **4** | 新しい API の設計と移行 | 互換の窓口（旧 API）は残す | タグ |

- **DB の統合を後にした理由**：実例はないにしても、DB は旧基盤のまま（Aurora）で、アプリだけ新しいものに切り替えられる方が手順として良い。既存の導入先は「アプリの差し替え（フェーズ1）→ DB の移行（移行 CLI、予定）」の2段階で移れる。旧スキーマに対する SQL を DB 統合で書き直す手戻りは、互換のための費用として受け入れる
- フェーズ1・2は PostgreSQL（旧スキーマ）のみ。
- ストレッチ目標は「移した範囲が、旧スキーマのまま Cloud Run で動く」（検証用の PostgreSQL は、Cloud SQL の最小構成か小さな VM。デプロイ時に決める）
- README の案で、移行 CLI は「今後の予定」とし、「既存の DB はそのままにアプリだけ差し替えられる」を前に出した

### フェーズ1の認証

| 項目 | 決定 |
| --- | --- |
| 方式 | 独自のセッション管理（毎リクエスト PostgreSQL に読み書き）をはがし、**旧 DB のパスワードで認証して JWT を発行**する |
| 毎リクエスト | proxy で JWT の署名を検査するだけ。DB には触らない。アクセストークンは短い有効期間、失効は更新トークンを無効にして実現 |
| 旧 API | ログインやセッション確認のエンドポイントは同じ形で残す。旧 DB のセッションのテーブルは使わなくなるだけで消さない（消すのはフェーズ3）。切り替え時に既存のセッションは無効になる（リリースノートに書く） |
| 更新トークン | **PostgreSQL の別スキーマ**（例：`shouya_auth`）。旧スキーマには触らない |
| 署名の鍵などのシークレット | **sops で暗号化した正本をレポに1つ**。NixOS（2階）は sops-nix、Cloud Run と Cloudflare には Pulumi が配る |
| 実行環境 | Hono のコードは Cloudflare Workers とコンテナ（Bun）の両方で動く形を保つ |
| OIDC | **初期フェーズでは扱わない**（発行する側か受ける側かは後で決める） |

- セッション確認の DB 読み書きとサービス間の確認の HTTP がなくなるので、性能の改善が一番はっきり出る箇所の一つ。比較の数字を取る対象に入れる
