# ADR-0011：JWT の署名を ES256 にし、検証の鍵を JWKS で公開する

| 項目 | 内容 |
| --- | --- |
| 状態 | proposed（提案） |
| 日付 | 2026-10-11 |
| 関連 Issue | #91 |
| 関連 ADR | ADR-0007（JWT の部分を置き換える。署名方式の固定、`kid`、短い有効期間、サービスでも検証する、は引き継ぐ） |

> 追記：この ADR は [ADR-0012](0012-ユーザー認証の外部委譲.md) に置き換えられた（提案中）。ユーザー認証と JWT の発行は外部の OIDC プロバイダーが担い、基盤は検証だけを行う。そのため、ES256 への固定、署名の鍵の所在、JWKS の公開は、0012 の決定に従って読み替える。ほかの記述は変えない。

## 背景（Context）

今の bootstrap は HS256（共有の鍵）で、proxy（Workers と Bun）が検証し、Go の検証はまだありません。HS256 では、検証に使う鍵がそのまま署名にも使えます。検証の鍵を持つ場所（Workers、Bun、Go）のどこか 1 か所から鍵が漏れれば、誰でもトークンを偽造できます。ADR-0007 の「サービスでも JWT を検査する」を実現すると、鍵を持つ場所がさらに増えます。

また、集会所の管理システムなど、外のアプリとの連携は OIDC を前提にします。連携の相手が自分で検証できる方式が要ります。

## 決定（Decision）

- 署名方式は **ES256**（P-256 の ECDSA）に固定する。トークンのヘッダーの `alg` は信じない（ADR-0007 を引き継ぐ）
- **署名の鍵は、認証の単位（Go）だけが持つ**。proxy と他の単位は署名の鍵を持たない
- **検証の鍵は公開する**：認証の単位が `/.well-known/jwks.json` で JWKS を出す。各鍵に `kid` を付ける
- proxy（Workers と Bun）と Go の各単位は、JWKS から取った公開鍵で検証する。JWKS は一定時間キャッシュし、知らない `kid` が来たら取り直す
- 鍵の入れ替え：新しい鍵を JWKS に先に載せ、署名を新しい鍵に切り替え、古いトークンの有効期間が切れてから古い鍵を JWKS から外す
- dev とテストでは、検証の鍵を JWK として設定で渡してもよい（JWKS の取得なしで動く）

EdDSA（Ed25519）ではなく ES256 を選ぶ理由：OIDC の周辺のライブラリと、Workers・Bun の WebCrypto、Go の標準ライブラリ（`crypto/ecdsa`）の、どこでも素直に使えるため。

## 結果（Consequences）

- proxy から秘密の鍵がなくなる。Workers から鍵が漏れて偽造される、という懸念がなくなる
- Go の各単位に検証の鍵を持たせる費用がゼロになり、ADR-0007 の「サービスでも検証する」がそのまま実現できる
- 連携するアプリは、JWKS を見て自分で検証できる
- 配る秘密情報から JWT の検証の鍵が消え、署名の鍵だけが残る（ADR-0010）
- 引き受けること：bootstrap の proxy の検証を HS256 から ES256 に書き換える。Go の標準ライブラリだけで JWS の検証を書く（`crypto/ecdsa`、`encoding/base64`、`encoding/json`）。署名の鍵の生成と JWKS の出力は、フェーズ1の認証の単位で作る
- ADR-0007 は、JWT の署名方式の部分だけをこの ADR で置き換える旨を追記する（ADR-0007 のほかの部分は変えない）
