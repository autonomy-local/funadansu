# ADR-0007：セキュリティの設計方針

| 項目 | 内容 |
| --- | --- |
| 状態 | proposed（提案） |
| 日付 | 2026-10-08 |
| 関連 Issue | なし |

## 背景（Context）

Funadansu は個人のデータを預かる基盤です。運用は運用者が自ら行う（Do It Yourself）ため、運用の段階でできることには限りがあります。脆弱性は、できるだけ設計の時点でなくしておく必要があります。

セキュリティは次の3つに分けて扱います。この ADR は2つめを決めます。

| 区分 | 扱う場所 |
| --- | --- |
| 開発者自身の事業継続 | このリポジトリの外 |
| **コードの脆弱性を設計の時点でなくす** | この ADR、[docs/security/threat-model.md](../security/threat-model.md) |
| 運用方式での担保（できうる限り） | [docs/operations/](../operations/README.md)、[SECURITY.md](../../SECURITY.md) |

## 決定（Decision）

脅威モデルを単位ごとに書き、下の方針を規約として守ります。方針に反する変更は、理由を ADR に書かない限り取り込みません。

| 領域 | 方針 |
| --- | --- |
| 脅威モデル | 守るもの（個人データ、鍵）、入口、信頼の境界を単位ごとに `docs/security/threat-model.md` に書く。単位の移行を終えるときに更新する |
| 認証（JWT） | 署名方式はサーバー側で固定し、トークンのヘッダーの `alg` を信じない。アクセストークンは短い有効期間にする。鍵には `kid` を付け、交換できるようにする。更新トークンは別スキーマに置き、ハッシュで保存して1回限りの使用にする。JWT に載せるのは最小限（操作者の ID、種別、`sid`、`exp`、`kid`）とし、権限は載せない |
| 旧 API の窓口の例外 | 旧 API のクライアントは更新トークンの手順を持たないため、**旧 API の窓口に限り**、JWT の有効期間を元の実装のセッションの期限に合わせることを認める（検討中。元の実装のクライアントがセッションをどう送っているかを確認してから決める）。その場合、失効は `sid` で行い、ログアウト・無効化した `sid` だけを失効リストに持つ。新しい API（フェーズ4）では例外を設けない |
| 信頼の境界（proxy → サービス） | proxy で検査した JWT をそのままサービスに渡し、**サービスでも署名を検査する**。経路（クラウドの IAM など）を信頼の根拠にしない。経路の制限（Cloud Run の ingress、VPS では localhost での待ち受け）は追加の一枚として重ねる |
| 移行期間のアダプター | 元の実装のサービスが残っている間は、operator の単位が元の実装のセッション確認の窓口を同じ形で提供し、中身は JWT の検査に置き換える。**一時的なもの**とし、元の実装のサービスが1つも残っていない状態になったら撤去する（差分台帳 D-001） |
| 権限の分離 | 本人確認・認証・認可は別の単位のまま保ち、統合のときも混ぜない。フェーズ1・2では、単位ごとに元の実装の DB（サービスごとの別 DB）への接続だけを持ち、他の単位の DB には接続しない。単位の間のやり取りは「外に出す関数の一覧」を通す |
| 入力の検査 | 入口で OpenAPI に照らして検査する。各サービスでも、受け取った値を信じずに検査する。解析の処理（パーサー）は Go の fuzzing の対象にする |
| 個人データ | 読み取り側（複製）には個人データを置かない。ログに個人データと秘密情報を出さない |
| 秘密情報 | コードと設定に平文で置かない。sops で暗号化した正本を1つ持ち、そこから配る。CI で秘密情報を検出する |
| 依存 | 依存を少なく保つ（Go は標準ライブラリを優先、DI のフレームワークを使わない）。バージョンとハッシュを固定し、更新は Renovate で受ける |
| CI | govulncheck、CodeQL・gosec、秘密情報の検出。GitHub Actions は SHA で固定し、ワークフローの権限は最小にする |
| 実装の規約 | `http.Server` のタイムアウト（とくに `ReadHeaderTimeout`）を必ず設定する、など Go の実装で守ることは `docs/conventions.md` に置く |
| 成果物 | Nix で再現可能なビルドにする。リリースには SBOM と Sigstore の署名を付ける。OpenSSF Scorecard で状態を測る |
| 脆弱性を見つけたとき | 作業を止め、詳細を Issue・PR・コミット・差分台帳に書かずに、SECURITY.md の窓口に報告する（元の実装で見つけた場合も同じ） |

### 理由

- 運用者のサーバーには開発者の手が届きません。設計でなくせるものは、設計でなくしておくのが最も確実です
- 認証の方式を変える（独自のセッションから JWT へ）ため、JWT の典型的な失敗（署名方式の取り違え、長すぎる有効期間、鍵を交換できない）を最初に塞いでおく必要があります
- 置き方には、クラウド（Cloud Run）と国内の VPS の両方があります。VPS にはクラウドの IAM がないため、どちらでも同じ仕組みで成り立つよう、経路ではなく JWT の検査を信頼の根拠にします
- 旧 API の窓口の例外は、互換を保つための形と割り切ります。例外の範囲を旧 API に限り、新しい API には持ち込みません
- 依存が少ないほど、サプライチェーンの攻撃の入口と、更新の手間が減ります
- 認証を取得したクラウドでも全面的な停止は起きます。再現可能なビルドは、別の場所で同じものを建て直すための前提になります

## 結果（Consequences）

### 検討した他の案

- **運用者の側で守ってもらう**：Do It Yourself の原則では、運用者の体制はまちまちです。初期値と設計で守る方を優先しました
- **外部の監査・認証（ISMAP など）を先に取る**：現在の規模と費用で現実的でないため、後の候補にしました
- **DI や ORM のフレームワークを使う**：依存と見えない処理が増えるため採りません
- **サービスは proxy を信頼し、JWT を検査しない**：Cloud Run の IAM に頼ることになり、VPS では成り立たないため採りません
- **旧 API でも短いアクセストークンにし、Cookie の更新トークンで proxy が黙って差し替える**：元の実装のクライアントがセッションをヘッダーで送っている場合は成り立たないため、確認が終わるまで保留しています

### 覆す条件

- 方針のどれかが、互換（OpenAPI への適合）と両立しないことがわかったとき
- 外部の監査を受ける段階になり、求められる基準と方針が合わないとき
- 元の実装のクライアントのセッションの送り方・期限の扱いがわかったとき（旧 API の窓口の例外を確定するか、取り下げる）
