# ADR-0003：本体のリポジトリとデプロイ用リポジトリを分け、秘密情報はその一方に 1 か所だけ置く

| 項目 | 内容 |
| --- | --- |

| 日付 | 2026-10-11（統合 2026-10-12） |
| 関連 Issue | #91（#17、#18、#19、#20） |
| 関連 ADR | ADR-0001（秘密情報とデプロイの原則を引き継ぐ）、ADR-0004（JWT の署名の鍵が基盤から消えたため、配る秘密情報が減る） |

この ADR は、旧 ADR-0009（リポジトリの分離）と旧 ADR-0010（秘密情報の正本と配布）を統合したものです。

## 背景（Context）

Funadansu は、運用者が自分で建てて運用する OSS です（Do It Yourself）。運用者ごとに、クラウドのアカウント、ドメイン、鍵、各種の ID が違います。

今のリポジトリには、本体のコードと一緒に、弊社の環境のための設定が入っています。

- `secrets/dev.yaml`（sops で暗号化した秘密情報。中身は dev のダミー）
- `.sops.yaml`（弊社の age の公開鍵）
- これから作る Pulumi のスタックの設定（GCP のプロジェクト ID、Cloudflare のアカウント ID、GCS のバケット名など）

これらは秘密ではないものも含みますが、攻撃の手がかりになります。暗号化した秘密情報も、一度公開すると取り消せず、将来鍵が漏れたときに履歴ごと読まれます。リポジトリを公開する前に、置き場所を決める必要があります。

秘密情報を使う場所は3つあり、読み方がそれぞれ違います。

| 使う場所 | 読み方 |
| --- | --- |
| Cloud Run（Go のサービス、1 階） | Secret Manager から読める |
| Cloudflare Workers（proxy） | Secret Manager は読めない。Workers の secret として入れる |
| 国内の VPS（Go のサービスと PostgreSQL、2 階） | クラウドの仕組みがない。ホストの上で復号する |

## 決定（Decision）

### リポジトリを 2 種類に分ける

| リポジトリ | 中身 | 公開 |
| --- | --- | --- |
| 本体（`funadansu`） | コード、OpenAPI、Pulumi のプログラム、NixOS のモジュール、文書、設定の見本（`deploy/example/`） | 公開 |
| デプロイ用（運用者ごと。弊社は `funadansu-deploy-autonomy`） | スタックの設定（`Pulumi.<stack>.yaml`）、sops で暗号化した秘密情報、`.sops.yaml`、各種の ID、運用者の手順のメモ | 非公開 |

- 本体には、特定の環境の値（ID、ドメイン、公開鍵を含む鍵の情報、暗号化した秘密情報）を置かない。見本の値だけを置く
- デプロイ用リポジトリは、本体を固定の版（タグかコミット）で参照する
- 本体の `deploy/example/` に、デプロイ用リポジトリの雛形（ディレクトリの構成、`.sops.yaml` の見本、`Pulumi.dev.yaml` の見本、置くべき ID の一覧）を置く

### 秘密情報の正本は 1 か所、配布は複数

1. **正本は 1 か所**：デプロイ用リポジトリの `secrets/<環境>.yaml` を、sops で暗号化して置く。これだけを正とする
2. **配布は複数**：正本から、使う場所ごとに配る。手で値を写さない

    | 配布先 | 配り方 |
    | --- | --- |
    | Cloud Run | Pulumi が Secret Manager に入れ、Cloud Run はそこから読む |
    | Workers | Pulumi の Cloudflare のプロバイダーで、Workers の secret として入れる |
    | 国内の VPS | sops-nix で、ホストの SSH の鍵から作った age の鍵で復号する |

3. **dev と本番を分ける**：ファイルも、暗号化の宛先（鍵の持ち主）も分ける
4. **鍵の持ち主と復旧**
    - 本番：sops の宛先を「Cloud KMS の鍵」と「オフラインの age の鍵」の 2 つにする。普段は KMS を使う（IAM で権限を絞り、使った記録が残る）。age の鍵は紙か YubiKey でオフラインに保管し、復旧のときだけ使う
    - dev：age の鍵を 2 人以上が持つ
    - 漏えいの疑いがあるときは、**鍵の入れ替え**（宛先の更新、`sops updatekeys`）と**値の入れ替え**（秘密情報そのものを新しくする）の両方を行う
5. **鍵を持たない方式を優先する**：秘密情報を配る代わりに、身元で認証できるところはそうする

    | 用途 | 方式 | 残る秘密情報 |
    | --- | --- | --- |
    | 利用者の認証のトークンの検証 | 外部の OIDC プロバイダーの公開の鍵（JWKS）で検証する。基盤は署名の鍵を持たない（ADR-0004） | なし |
    | Cloud Run から PostgreSQL | Cloud SQL の IAM による DB 認証 | なし |
    | VPS の Go から PostgreSQL | 同じホストの Unix ソケットで peer 認証 | なし |
    | Pulumi の状態の秘密 | 秘密の保護を Cloud KMS に任せる（パスフレーズを使わない） | なし |
    | CI から GCP | Workload Identity 連携 | なし |
    | CI から Cloudflare | 権限を絞った API トークン | トークン 1 つ |
    | VPS の Cloudflare Tunnel | — | Tunnel のトークン |
    | バックアップ | — | 暗号化の鍵、R2 のアクセスキー |

    プロバイダーの管理の操作（ユーザーの作成など）に鍵が要る場合は、ここに追加する（ADR-0004 の確認事項）

### デプロイの流れ

本体は版を付けてリリースするだけで、誰がそれを使うかを知らない。デプロイ用リポジトリが本体の版を取りに行く。本体の CI からデプロイ用リポジトリを発火させない（本体に非公開リポジトリへの権限を置かないため、ほかの運用者も同じ流れに乗れるようにするため）。

1. 本体でタグを切る。CI がビルド、テスト、署名、SBOM を行い、成果物（コンテナのイメージ、Workers のバンドル、flake のタグ）を公開する
2. デプロイ用リポジトリで、本体の版を上げる（flake の入力、イメージの digest、Pulumi の設定）
3. `pulumi preview` で差分を確かめてから、`pulumi up` と `nixos-rebuild` で反映する
4. 本番は別のスタックで、同じ版に上げてから反映する

**当座はローカルで行う**：2〜3 は、手元のデプロイ用リポジトリから手で実行する（デプロイの最小の手順）。そのうえで次を守る。

- 実行はスクリプト 1 本（例：`./deploy.sh dev`）にまとめ、デプロイ用リポジトリに置く。後で CI に移すときにそのまま呼べるようにする
- スクリプトは鍵や資格情報を持たない。開発者が手元の CLI で済ませた認証（`gcloud auth application-default login`、VPS への SSH など）をそのまま使う。CI に移したときは、同じスクリプトが Workload Identity 連携の身元で動く。スクリプトは認証の取り方を気にしない
- 道具の版は、デプロイ用リポジトリの `nix develop` で固定する（pulumi、sops、gcloud、nixos-rebuild など）
- 実行の前の確認をスクリプトに入れる：gcloud のアカウントとプロジェクトが対象のスタックと合っているか、Cloudflare の API トークンが環境変数にあるか、ブランチが main で origin と一致しているか。本番は、スタックの名前を打ち直させてから進む
- Cloudflare の API トークンは平文のファイル（`.env` など）に置かない。sops で暗号化したデプロイ用の秘密情報から、実行のときだけ環境変数に読み込む
- コミットしていない変更があるときは、スクリプトが止まる
- 反映した版と日時を、デプロイ用リポジトリのコミット（またはタグ）として残す

版を上げる PR を自動で立てる（Renovate）、PR で `pulumi preview` を流す、マージで反映する、という CI への移行は、運用者が増えるか、本番の反映が頻繁になった時点で行う。

## 結果（Consequences）

- 本体を公開しても、弊社の環境の情報は外に出ない
- 運用者は、雛形をコピーして自分のデプロイ用リポジトリを作る。弊社も同じ手順を踏むので、手順書が実際に使われ続ける
- 配る秘密情報は、Cloudflare の API トークン、Tunnel のトークン、バックアップの暗号化の鍵と R2 のアクセスキーになる。JWT の署名の鍵は、基盤から消えた（ADR-0004）
- 本番の鍵を使った記録が KMS に残る。鍵を失っても、オフラインの age の鍵で復旧できる
- 引き受けること
  - リポジトリが 2 つになり、本体の変更とデプロイの設定の変更が別の PR になる。本体の版を上げるときは、デプロイ用リポジトリで参照を更新する
  - Cloud KMS と Workload Identity の設定が、最初の環境づくり（タスク 5.1）に加わる。2 階の運用者が GCP を使わない場合は、本番の宛先を「age の鍵 2 つ（普段用とオフライン）」に読み替える手順を `docs/operations/secrets.md` に書く
- 公開の前に、本体の履歴全体を秘密情報の検出の道具（gitleaks など）で検査し、`secrets/` と `.sops.yaml` を本体から外す
- `docs/operations/secrets.md` は、本体には手順と見本だけを書き、環境の値はデプロイ用リポジトリに書く
