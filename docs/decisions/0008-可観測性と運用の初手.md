# 0008. 可観測性と運用の初手

- 日付: 2026-10-10
- 状態: 提案

## 背景

Funadansu は、置き方が二つあります（ADR 0006）。

- 1階：Cloudflare Workers（proxy）と Cloud Run（Go のサービス）。マネージドの監視の仕組みが使える
- 2階：国内の VPS と NixOS。マネージドの監視の仕組みはない

開発の初期は運用の手が限られるため、監視はクラウドの仕組みに任せたい。一方で、2階の運用者が同じ考え方で運用できること、後から送り先を変えられることも必要です。

この ADR は、可観測性（トレース、ログ、メトリクス）と運用の**初手**だけを決めます。SLO やエラーバジェット、当番の体制のような本格的な SRE の取り決めは、運用の実績が出てから別の ADR で決めます。

## 決めたこと

コードは OpenTelemetry（OTel）の作法で書き、送り先・量・権限はデプロイの設定（1階は Pulumi、2階は NixOS）で明示する。

### コードの側で守ること

| 項目 | 決めたこと |
| --- | --- |
| 依存 | 各単位のコードは OTel の API（トレース、メトリクスの記録）だけを呼ぶ。送り先（エクスポーター）は `main.go` の配線で一度だけ決める |
| 設定 | 送り先、サービス名、環境名は OTel の標準の環境変数（`OTEL_EXPORTER_OTLP_ENDPOINT`、`OTEL_SERVICE_NAME`、`OTEL_RESOURCE_ATTRIBUTES` など）で受け取る。コードに書かない |
| 文脈の引き継ぎ | W3C の `traceparent` を標準にする。proxy（Workers と Bun の両方）から Go へ必ず引き継ぎ、Go では `context` に乗せて単位の間の関数呼び出しにも流す |
| ログ | `log/slog` の JSON。トレースの ID とスパンの ID を必ず入れる。1階では Cloud Logging が結び付けられる項目（`logging.googleapis.com/trace`）の形でも出す。Bun の proxy のログも同じ項目の名前に揃える |
| 項目の名前 | OTel の標準の名前（セマンティック規約：`http.request.method`、`http.route`、`db.system` など）を使い、クラウド独自の名前は使わない |
| 個人データ | スパンの属性・ログ・メトリクスに、URL のクエリ、ヘッダー、リクエストの本文、JWT、クッキーを入れない。`http.route` は `/books/{id}` のような型で記録する。メトリクスのラベルに利用者の ID のような種類の多い値を入れない（ADR 0007） |
| 量 | トレースは親の判断に従うサンプリング。割合とログの水準は環境変数で変えられるようにする |
| Go の実行環境 | `GOMEMLIMIT` を割り当てメモリの約9割に設定する（デプロイの設定で）。起動時に `GOMAXPROCS` とメモリの上限の値をログに出す |

### デプロイの側で明示すること

| 持ち場 | 中身 |
| --- | --- |
| 1階：Pulumi | Cloud Run の環境変数（`OTEL_*`、サンプリングの割合、ログの水準、`GOMEMLIMIT`）。サービスアカウントの権限（トレース・ログ・メトリクスの書き込みだけ）。Workers の observability の有効化とソースマップのアップロード |
| 2階：NixOS のモジュール | OpenTelemetry Collector を一つ置き、受け口にする。送り先は運用者が選ぶ（最初はファイルや journald でもよい）。環境変数は1階と同じ |
| 秘密情報：sops | 外部の監視サービスに送る場合の API キーなど |

### 初手で使う監視

| 対象 | 初手 |
| --- | --- |
| proxy（Workers） | Cloudflare のダッシュボード（Workers Logs、必要なときのオンデマンドの CPU・メモリのプロファイル） |
| Go（Cloud Run） | Cloud Trace、Cloud Logging、Cloud Monitoring |
| 2階 | Collector を経由して、運用者が選んだ先 |
| アラート | 置くなら最小限（死活監視、エラー率）とし、IaC に残す。何が起きたら誰に知らせるかは `docs/operations/` と対応させる |

## 理由

- 初期は運用の手が限られるので、クラウドの監視の仕組みに任せるのが一番安い
- OTel の作法で書いておけば、送り先を変えてもコードに触らずに済む。特定のクラウドに監視を縛られない
- 2階にはマネージドの監視がないため、Collector で差を吸収できる構えにしておく必要がある。1階と2階で同じコードを動かせる
- 送り先・量・権限を IaC と NixOS で明示すれば、どこに何を送り、誰に何を許したかが記録に残る（ADR 0007 の最小権限）
- 監視のデータは、放っておくと個人データの漏れ道になる。項目の名前と載せないものを先に決めておく

## 検討した他の案

- **最初から自前の監視の基盤（Grafana、Prometheus など）を立てる**：運用の手間が初期には重すぎるため、採らない。2階の運用者が選べるように、Collector の先として残す
- **クラウドごとの SDK やライブラリで直接計測する**：送り先を変えるときにコードの書き換えが要り、2階で同じコードを動かせないため、採らない
- **本格的な SRE の取り決め（SLO、エラーバジェット、当番）をこの時点で決める**：運用の実績がないまま数値を決めても当てにならないため、後に回す

## 後で決めること

- SLO と、その測り方（何を「良い応答」とみなすか）
- エラーバジェットと、それを使い切ったときの扱い
- アラートの基準、当番と連絡の体制（一人運用を前提にするか）
- 事故の対応の手順（`docs/operations/incident.md`）と、事後の振り返りの型
- ダッシュボードの標準の形
- 容量の計画、常時のプロファイル、負荷の試験の定期化（P0-8 の測定の道具を元に）

## 覆す条件

- クラウドの監視の費用が、OTel の Collector を自前で回す費用を明らかに上回ったとき
- 2階の運用者から、Collector の構成が重すぎるという声が続いたとき
- 本格的な SRE の取り決めを決める段階になったとき（この ADR を土台に、新しい ADR を起こす）
