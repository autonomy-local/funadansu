# ADR-0004：ユーザー認証と JWT の発行は外部の OIDC プロバイダーに任せ、基盤は検証だけを行う

| 項目       | 内容                                                          |
| -------- | ----------------------------------------------------------- |
| 状態       | accepted（採用）                                                |
| 日付       | 2026-10-12                                                  |
| 関連 Issue | #91（#94、#95 に影響。PR の説明を参照）                                  |
| 関連 ADR   | ADR-0003（配る秘密情報が減る）、ADR-0001（検証と入力の検査の原則を引き継ぐ）。旧 ADR-0011 の JWT の方式を置き換える |

## 背景（Context）

この基盤を使う地域は、開発のチームも運用のチームも小さく、専門の人材が薄いことを前提にしています。認証の署名の鍵の生成・保管・入れ替え・漏えい時の対応まで負わせるのは、どの環境でも現実的ではありません。KMS を使う場合でも、設定と運用の負担が残ります。

また、基盤が発行する側のトークン（ブローカー側のトークン）は、次期の基盤で DID/VC に移すときに外す前提です。ユーザー認証のために、新しく署名の仕組みを作り込む理由は小さいです。

## 決定（Decision）

1. **ユーザー認証と JWT の発行は、OIDC に準拠した外部のプロバイダーが担う**。基盤は署名の鍵を持たず、**検証だけ**を行う

2. **プロバイダーは差し替えられるようにする**。特定のサービスに固定しない
   - マネージドの基盤（Firebase Authentication、Auth0、Amazon Cognito など）も、OSS（Keycloak など）も使える
   - どれを使うかは、地域ごとの設定で決める。運用の体制が薄い地域にはマネージドを勧め、自前で持ちたい地域には OSS を案内する
   - 最初に実装するのは Firebase Authentication。次に、Keycloak を自前で運用する場合を実装する。この2つで、ほかのプロバイダーにも広げられる見立てとする

3. **検証の設定は、標準の OIDC の項目に絞る**

   | 設定             | 内容                                                      |
   | -------------- | ------------------------------------------------------- |
   | `issuer`       | 信頼する発行者。トークンの `iss` と完全に一致させる                          |
   | `audience`     | トークンの `aud` に含まれるべき値（プロバイダーごとの実装で扱いを決める）          |
   | `allowed_algs` | 許可する署名方式（既定は ES256 と RS256）。`none` と HS256 は許可しない      |
   | `jwks_uri`     | 公開鍵の場所。discovery（`/.well-known/openid-configuration`）から取れる場合は省略できる |

4. **検証は Go（サービス側）で行う**（ADR-0001 の原則を引き継ぐ）
   - proxy は JWT を検証しない。検証は、トークンを受け取るサービス（Go）が行う
   - プロバイダーごとの検証は、個別の実装として書く。実装は共通のインターフェースの裏に置き、プロバイダーを増やすときは実装を1つ足し、設定を1つ足す（既存の実装は変えない）
   - 共通の部分（JWKS の取得とキャッシュ、`kid` の照合、`alg` の許可リスト、`exp`・`nbf` の確認）は、実装が共有して使う
   - 個別の実装が確かめること：`iss` の完全一致、`aud` の扱い（プロバイダーごとに違う）、トークンの種類の確認（ID トークンかアクセストークンか）
   - ヘッダーの `alg` は信じない。`allowed_algs` と照合し、鍵の種類と合うかも確かめる
   - JWKS は一定時間キャッシュする。知らない `kid` が来たときは取り直すが、取り直しの間隔に下限を設ける（偽の `kid` で JWKS の取得先に負荷をかけられないようにする）
   - dev とテストでは、検証の鍵を JWK として設定で渡してもよい
   - Firebase Admin SDK は、検証には使わない。Go の標準ライブラリで書く方針（AGENTS.md）と、プロバイダーを固定しないため

5. **内部のユーザー識別子を、プロバイダーから独立させる**
   - 基盤が内部の ID を払い出し、`(issuer, sub)` との対応を持つ
   - `sub` を、そのまま主キーや他のデータとの結びつきに使わない（プロバイダーを替えたときに、全員が別人になるため）
   - 対応をどの時点で引くかは、確認事項 1 による

6. **プロバイダーに預ける情報は、基盤のガイドラインの線引きに従って限る**
   - 預けてよい：`sub` と、ログインに使う識別子（メールアドレスなど）。ただし、個人情報にあたりうる点は確認事項 3
   - 預けない：氏名やマイナンバーなど、特定の個人を識別できる情報。表示名の欄にも氏名を入れない（仮名にする）
   - 同意の状態、PxR のデータ、地域の属性は、プロバイダーに置かず、トークンのカスタムクレームにも入れない。これらは基盤が持つ
   - プロバイダーの処理の場所は、選定の基準にしない。預ける情報が上の範囲に限られるためである。どこで処理されるかは、プロバイダーごとに確かめて、運用者向けに `docs/operations/` に書く

7. **基盤は自分のトークンを新たに発行しない**。利用者が使うトークンは、プロバイダーが発行したものを、サービスが検証する（決定 1 の帰結）。既存のブローカー側のトークンは、次期基盤で DID/VC に移すときに外す前提で、この ADR では扱わない

8. **proxy の責務は薄くする**
   - 行うこと：リクエスト量の制限（レートリミットを含む）、OpenAPI に照らした入力の検査。不正な値は proxy で止め、後ろのサービスには流さない
   - 行わないこと：認証と認可（サービス側が行う）
   - 防御：Cloudflare の利用を強く推奨する。Cloudflare を使わず自前で置く場合は、IP 制限などの防御は運用者の責務になる（運用の手引きに書く）

## 検討した他の案

| 案                         | 採らなかった理由                               |
| ------------------------- | -------------------------------------- |
| 自前で発行する（旧 ADR-0011）     | 署名の鍵の保管・入れ替え・復旧を、体制の薄い運用者が担うことになる        |
| 特定のサービス（Firebase など）に固定する | 地域ごとの事情（クラウドの選択、データの所在）に合わず、乗り換えも難しくなる  |
| 検証に Firebase Admin SDK を使う | Firebase 専用になり、プロバイダーを替えるときに検証の部分を書き直すことになる。Go の標準ライブラリの方針（AGENTS.md）にも反する |

## 結果（Consequences）

- 基盤から JWT の署名の鍵がなくなる。配る秘密情報が減る（ADR-0003）
- 認証の単位（フェーズ1）は、トークンの発行と JWKS の公開を作らなくてよい。代わりに、検証と、`(issuer, sub)` と内部 ID の対応を作る
- 連携するアプリも、同じプロバイダーの JWKS を見て検証できる
- 引き受けること
  - ES256 だけに固定する旧案をやめ、許可リスト方式にする。bootstrap の proxy の検証は HS256 のままなので、Go の検証と合わせて書き換える
  - 基盤ごとの仕様の違い（鍵の公開の場所、`sub` の形、discovery の有無、`aud` の扱い、トークンの種類）を、実装のときに確かめる。discovery がない基盤は、`jwks_uri` を直接指定する
  - 主な基盤の確認結果（2026-10-12）：
    - Firebase Authentication は RS256 で署名し、`iss` は `https://securetoken.google.com/<プロジェクトID>`。JWK 形式の公開鍵（RSA、RS256）は `https://www.googleapis.com/service_accounts/v1/jwk/securetoken@system.gserviceaccount.com` で取れることを確認した。discovery の有無は未確認
    - Amazon Cognito は RS256 で、`iss` は `https://cognito-idp.<リージョン>.amazonaws.com/<ユーザープールID>`。JWKS と discovery がある（公式の文書による）。アクセストークンには `aud` がなく、`client_id` が入る
    - どちらも ES256 ではないため、ES256 固定の方針では使えない
  - プロバイダーが止まると、新しくログインできなくなる。検証済みの JWT の有効期間の間は動く
- 旧 ADR-0011（JWT の署名を ES256 にする案）は、この ADR に置き換えたため削除した。経緯は git の履歴に残す。ADR-0001 の JWT の部分も、この ADR で改めた

## 実装の前に確かめる事項

次の4点は、この ADR では決めていません。実装の前に決めます。

1. **内部 ID の引き方**：毎リクエストは署名の検査だけで、DB には触らないという原則（AGENTS.md）と、`(issuer, sub)` から内部 ID を引く処理は両立しない。候補は、(a) 内部 ID をプロバイダーのカスタムクレームに入れる（プロバイダー側の仕組みに依存し、設定に管理の鍵が要る）、(b) 対応をキャッシュして引く（原則に反する）、のどちらか
2. **旧 API の窓口の `sid`**（ADR-0001）：プロバイダーのトークンには、基盤が決めた `sid` がない。旧 API の窓口の例外を採るかどうかに直結する
3. **個人情報の前提**：ログインに使うメールアドレスと `sub` は、個人情報にあたりうる。「非個人情報だけを預ける」という前提の書き方を、「氏名・同意・データを預けない」に改めるか、仮名のログイン ID を使うかを決める
4. **トークンの種類**：ID トークンか、アクセストークンか。Firebase の最初の実装で決め、Keycloak の実装でも同じ扱いにできるかを確かめる
