# ブランチ戦略：トランクベース開発

Funadansu は、トランクベース開発で進めます。

## きまり

- **`main` が唯一のトランク**です。`main` は常にテストが通り、デプロイできる状態に保ちます
- 作業は `main` から切った**短命のブランチ**で行い、**PR で `main` にマージ**します。`main` へ直接 push はしません
- ブランチは**小さく、早くマージ**します。目安は1つの Issue につき1つのブランチと1つの PR で、数日以内にマージできる大きさにします。長引きそうなときは Issue を分けます
- マージしたブランチは削除します。マージ済みのブランチに作業を積み足さず、続きは新しいブランチで始めます
- `develop` や `release/*` のような**長く残るブランチは作りません**。リリースは `main` のコミットにタグを付けて行います（[移行のフェーズ](migration-phases.md)の「リリース」欄）
- `main` との差が開いたら、早めに `main` を取り込みます

## 作業の単位は Issue

作業は Issue から始めます。Issue には、その作業の**終了条件**を書きます。PR のレビューでは、終了条件を1つずつ満たしているかを確認します。

- Issue の書き方：[Issue テンプレート（タスク）](../.github/ISSUE_TEMPLATE/task.yml)
- PR の本文には、対応する Issue（例：`Closes #12`）と、終了条件ごとに満たした根拠を書きます

## 未完成のコードを `main` に入れるとき

基本は、1つの PR で完結する大きさに Issue を分けることで、未完成のコードを `main` に入れずに済ませます。
それでも途中の状態をマージする必要があるときは、次のどれかで `main` のデプロイできる状態を保ちます。必須ではなく、必要になったときの既定の方法です。

- まだどこからも呼ばれない形で入れる（ルーティングやエントリーポイントにつながない）
- 設定や環境変数による機能フラグで、既定は無効にしておく
